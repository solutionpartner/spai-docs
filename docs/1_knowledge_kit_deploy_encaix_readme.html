Encaix · Kit d'oferta SPAI ➜ Business AI OS (deploy governat)

ID document: SPAI-KP-DEPLOY-001 · Versió: 1.0 · Data: 2026-10-16 Autor: SolutionPartner.AI · Estat: proposta d'encaix (no acredita desplegament) Fonts: spai-build-pack/SPAI_Hermes_Build_Pack_v1_1/ (Build Pack v1.1) + fases 1–21 a spai-fases-historic/ + kit deliverables/kits/ (kit01 + kit02).

Grau d'evidència. Aquest mapa connecta dues coses que existeixen per separat: el kit d'oferta (producció real, provat) i el Build Pack (paquet documental de construcció, no una release desplegada). El "pont" (secció 3) és a construir.

1. Resum en una frase

El kit produeix el model del tenant (què automatitzar i com). El Build Pack descriu com es desplega un tenant. Falta el pont que faci que el model del kit alimenti l'onboarding del tenant de manera guiada/automàtica.

Capa 4 · SPAI central (DISSENYAT — Control Plane)

  • OPTIMUS — governa, ordena canvis i actualitzacions als clients.
  • Signer (Ed25519) — releases signades (build immutable + manifest signat).
  • Action Gateway — única frontera de mutació model-facing; denegació per defecte.
  • Aprovació humana — obligatòria segons política, independent de l'onboarding.

Capa 5 · Tenant del client (DISSENYAT — aïllat per client)

  • Hermes del client (Argon) — raonament + operació governada; les seves skills són els automatismes del client.
  • n8n — fluxos importats.
  • Business OS — runtime + Approval Engine.
  • runtime-sync · heartbeat — estat i senyal de vida.
  • deploy worker — fa pull del que està aprovat i aplica via handler local.

3. Flux de desplegament (el que ja està dissenyat al Build Pack)

CI construeix → signer signa (Ed25519) → Control Plane registra
→ aprovador humà autoritza → deploy worker del tenant fa pull i valida
→ handler local aplica → health + estat "applied" verificats
  • Rollback: POST /deployments/{id}/rollback (validar esquema de l'API instal·lada).
  • Backup/restore: RPO/RTO per client; un rollback de codi NO desfà un efecte extern (una factura enviada), això és anàlisi separada.
  • Govern: Optimus ↔ Hermes per MCP amb compte supervisor_operator limitat. Mutacions via propose_action → aprovació → execute_approved_action. Mai root/SSH.

8. Claus i CA — mapeig complet (resultat de revisar el codi real)

La baseline té 5 sistemes de claus separats. Cada un té un script de generació (a scripts/) i una política de custòdia clara: la clau privada no entra mai al Control Plane ni als VPS dels clients, només les públiques/verificadors.

# Sistema (script) Algoritme Ús On viu la clau privada
1 Release signing (generate_release_keys.py + sign_release_manifest.py) Ed25519 Signa els manifests de release (digest sha256:). El Control Plane els verifica amb SP_RELEASE_PUBLIC_KEY_PEM/PATH abans d'acceptar. Offline / CI-secret-manager. Només la clau pública es munta al Control Plane i als clients.
2 License leases (generate_license_keys.py + license_signer_worker.py) Ed25519 Signa les llicències (verify_lease) — governa package_allowed, allow_ai, allow_write, allow_deploy. Fora del Control Plane; només la pública hi va i als tenant_runtime.
3 Break-glass (generate_break_glass_keys.py + issue_break_glass.py) Ed25519 Accés d'emergència independent de l'onboarding. Offline, custodiada; només pública muntada al Control Plane.
4 Client PKI / mTLS (generate_client_pki.sh + cert_fingerprint.py) ED25519 CA + client Identitat de cada tenant a l'edge (Caddy requereix mTLS a clients.*). La CA emet un cert per tenant; l'enrolament registra el sha-256 al Control Plane i activa SP_CLIENT_AUTH_MODE=key+mtls. client-ca.key offline; només client-ca.pem al gateway. Única clau privada per tenant al seu VPS (el seu cert).

8. Catàleg de mòduls del producte (venda i instal·lació governada)

Decisió (2026-10-17). SalesPower/BusinessPower es ven per separat del Business AI OS + automatitzacions IA. Els mòduls no s'implementen tots de cop (no construeixis tot Odoo): s'activen a la carta, des de la Configuració del dashboard, i el desplegament és governat.

Flux (activació en un clic)

  1. Dashboard (Configuració → Mòduls) llista el catàleg: cada mòdul té id, àrea (CRM/ERP/IA), inclòs (a la llicència bàsica) o preu (extensió de pagament).
  2. L'usuari fa clic a Activa:
  3. si el mòdul és de pagament i el tenant no el té → es mostra el pagament.
  4. en tot cas s'encarrega l'Argon (l'Hermes del tenant).
  5. Argon demana a Optimus (orquestrador central) per API.
  6. Optimus retorna el codi desplegable (manifests, imatges/artifacts, workflows n8n, skills, MCPs, secrets refs) + rails/instruccions d'implementació.
  7. Argon ho instal·la al tenant (pull, model governat — mai pujar des del central).

Regles

  • inclòs: mòdul que ve amb la subscripció bàsica del tenant (activació immediata).
  • preu: extensió addicional; l'activació requereix pagament si no està coberta.
  • Un mòdul GUIAT per l'operació es registra com a component (agent|skill|connector|runtime|workflow) al template d'onboarding — el mateix mecanisme que el kit ja genera.
  • Argon mai s'autoaprovacà un mòdul de pagament: la facturació i l'aprovació passen per Optimus.
  • El codi desplegable viatja signat; el handler local valida digest/URI (model pull establert).
